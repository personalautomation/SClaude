All agents in one chat, each checking the others. Pleasant to watch, and of little use by the end.

What I learned

  • Different models do give genuinely different perspectives.
  • Less context means fewer tokens.
  • Agents polished corner cases no user would ever reach.
  • Code size and token cost grew faster than the value. Past a certain complexity AI struggles; strict frameworks help.
  • Then a startup asked for the same: one model in every role was voices inside one head. One idea survived: manage the context, and the tokens follow.

We did not roll it out. Speed is addictive; control has to be designed.

Why · the durable lesson

Do not make the model the process engine

Prompts are not guarantees. Even with explicit instructions and IMPORTANT warnings, a model invents statuses, switches language and ignores predefined options, and over time the process drifts. So the process moved into code.

1 · Controlled context

A session per stage, with an explicit hand-off. Less irrelevant context, fewer tokens.

2 · Controlled models

The strongest model for judgement, a cheaper one for the PR, none for deploys and gates.

3 · Hard constraints

Allowed actions are enforced, not requested. The agent cannot leave the path.

4 · Feedback loops

Where the agent struggles is logged and turned into a better rule.

Lower token spendControlPredictable processScales without load on the team

Less spectacular than a chat of agents. The more work moves into the orchestrator, the cheaper each feature gets.

Why · division of labour

The model handles judgement. The orchestrator handles the rest.

Remembers which step every feature is on, and resumes after any interruption

Gathers the context for each step and renders its prompt

Sets up a sandbox per feature: worktree, dev server, database

Runs the tests locally, on the preview and on production

Deploys, and rolls production back when it goes red

Keeps the issue, the pull request and the board up to date

Same operation every runNo interpretationZero tokens

If a script can do it, the model should not.

The token budget goes to planning, writing and reviewing code, which is where a model is actually better than a script.

The safety model

Contain. Curate. Control.

Docker's three layers for agent security, applied to a whole coding workflow. Each one is a separate answer to "what if the agent gets it wrong?"

Contain

Limit the blast radius

A mistake stays inside one feature.

  • A copy of the repository and a branch per feature
  • Its own dev server, address and database
  • Its own preview; production is never a feature's target
  • A failed release rolls back without touching anyone else's
more → the next slide
Curate

Construct the agent's world

Before a session starts, the orchestrator decides what it gets.

  • The context for this stage, and nothing stale
  • The tools and permissions this stage needs
  • The model and effort the stage is worth
  • The instructions: sclaude's, the team's, the developer's
more → the steps
Control

Enforce at the moment of action

Rules are executable, not advisory.

  • Hooks refuse a forbidden command as the agent tries it
  • Merge, main and production stay a person's call
  • Every refusal is logged
  • and reviewed: the feedback loop

How a feature flows · contain

Every feature in a sandbox of its own

The first C, contain the blast radius. With an agent per feature a developer runs several in parallel, and in one shared checkout they collide: one migration wipes another's data, one sign-in signs you out of the next.

Its own code

A worktree

A separate copy of the repository on its own branch. Edits meet only in the pull request.

Its own address

feature.localhost

A dev server per feature behind its own address, so cookies and sign-ins stay apart.

Its own database

Supabase in Docker

Filled from the main local database or the seed. A migration reaches nothing else.

Its own preview

Vercel per branch

QA checks each feature at its own deployed address, never on a shared staging server.

  • Idle for half an hour: stopped, database included, data kept; it starts again on the next visit
  • No Docker running: sclaude starts it, and falls back to the shared database only when it cannot, saying so
  • Removed with the feature when it is done; production is never a feature's target

Parallel work without a shared mess.

How a feature flows · curate: pay for thinking

Each step gets its own model, permissions and exit

The second C, curate: for every step the orchestrator builds the agent's world, its context, tools, model and instructions.

StepModelMay doCloses only on
1 · PlanOpus · highDiscuss and write the plan; no code at allA plan a person approved, with criteria
2 · CodeOpus · mediumImplement, check in Chrome, commitA person's yes and green tests
3 · Pull requestSonnet · mediumManuals and the pull requestA pull request that exists on GitHub

Every step starts a fresh session. Only the approved plan, with its criteria, is carried forward. Nothing stale leaks into the next step.

A step closes on evidence, never on a model saying "done". Ctrl-C, a usage limit or a closed laptop closes nothing; the conversation resumes.

How a feature flows · token secrets

Six habits that cut the token bill

The kind of know-how that used to live in one person's head. Most of it is built into the flow; the rest is shared as team practice.

1 · The cache lives an hour

A subscription keeps the prompt cache for an hour (five minutes on credits or an API key). Warm, the context is re-read at a tenth of the price or less; cold, it is paid in full. Take on no more parallel features than you can answer within the hour.

team habit
2 · A fresh session per step

Stale context is paid for on every message. Starting clean costs nothing; compacting a long conversation is itself a large request.

built in
3 · The right model per step

Opus where judgement matters, Sonnet for the pull request and the write-up, no model at all for deploys and gates.

built in
4 · Scripts before tokens

Deterministic work runs as scripts. A hook can cut a ten-thousand-line log to its failures before the model reads it.

built in
5 · Lean always-on context

CLI tools rather than MCP servers; workflow instructions as skills that load on demand; CLAUDE.md under 200 lines.

team habit
6 · Delegate the noisy parts

Sub-agents keep long outputs out of the main context. Agent teams cost about seven times a single session.

built in

Review and decisions · AI review done deliberately

How sclaude avoids the four ways review goes wrong

FailureWhat sclaude does about it
Finds nothingThe review must actually run on the latest commit. A green check that reviewed nothing is shown as such, and the step waits for a running review.
Endless roundsA decision a person made is recorded as "left as it is" and the next review is told not to raise it again. A fix that would undo an earlier fix is stopped and put to the person.
Burns tokensOne round per session: a fresh, small context with only the threads still open. Fixes go to sub-agents, and suggested new abstractions are weighed against the review surface they add.
Stalls on a personThe agent fixes and replies. The person only sees the few findings it disagrees with, as an explicit yes or no question.

Review runs in GitHub Actions or on the developer's own machine. Findings that are real but out of scope go to the monthly review rather than being fixed now or lost.

"Tell the reviewer to flag only gaps that affect correctness or the stated requirements."Anthropic, Claude Code best practices

Control · the main know-how 1 of 4

Start with the tools locked down, on purpose

An agent with every tool open starts steering the work: it picks the scope, merges what it likes, touches what it should not. Then the model controls development, not us.

Refused as it happens
  • Writing code while planning
  • Merging: a person's decision
  • Pushing to main, force-push, skipping hooks
  • Promoting migrations, switching to production
  • Resolving a person's review decision alone
  • Deploying to production without asking: no default answer, and "anyway" when QA never saw it

Rules come in layers

sclaude core

Merge, main, force. Nobody lifts these.

Integration presets

The usual dangers of Vercel and Supabase.

The product's team

Its own bans; may lift a preset's.

One developer

Personal additions; lifts nothing above.

But locks alone fail too

A ban that blocks real work makes people fight the tool, switch it off or work around it. Locking down works only when someone reads what the locks caught.

Tight by default. Loosened by evidence, never by habit.

Feedback loops · the main know-how · 3 of 4

The retrospective is how the team learns

Before a feature's sandbox is removed, a session reads everything the developer saw and typed during the whole feature, and gives three answers.

1 · What you may have missed

A warning that scrolled past, a promise a session did not keep, a follow-up never filed. Acted on while the sandbox still exists.

2 · How you could work better

Where you waited, where you went round the same loop, where an earlier or clearer answer would have saved a session.

3 · What sclaude could do better

A misleading message, a stalled step, work a session did that a script could have done. Named down to the file.

Plus: what went well

Each retro also names what worked and is worth keeping. Across a team, that is how best practices surface: from real features, with evidence, without a meeting.

The rule: facts only

Every point quotes a line from the recording or names a file and field. An empty section is a fine answer. Nothing is padded to look useful.

Where a lesson ends up, and who decides

A lesson starts with one person and climbs only as far as it proves itself.

One developer

A team rule

Once it proves itself, a product maintainer lifts it into the team's rules. Now everyone on the product works that way.

decided by a maintainer
→
Every product

A sclaude default

A lesson that holds everywhere is collected as a proposal and goes to sclaude as a deliberate pull request. Every machine gets it on its next command.

decided by sclaude's maintainers

Nothing changes the process by accident. Everything that should change it, can.

Review sessions never edit sclaude itself: a hook keeps them out. They change the product, and leave sclaude's maintainers a note.

Manageable means

Doable

Runs on the laptops a team already has, on free tiers, installed with one script.

Controllable

A fixed path, gates on evidence, rules that hold, people at every decision.

Affordable

Tokens spent on thinking only. Everything repeatable is a script.

The orchestrator owns the process. AI does what the process asks. Building it is closer to project management than to programming: design the flow, set the constraints, track the deviations, resolve the conflicts between rules.
