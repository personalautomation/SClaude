**If a restriction blocks you** — a missing tool, a rejected command, a workaround you had to take — append a line to `.sclaude/local/feature/friction.log`: what you needed and why. A separate session reads this after every session and fixes the orchestrator. This is a request, not a complaint: the restrictions were configured blind, and some of them are wrong.

**A rule you would propose for the project's `CLAUDE.md` goes there too**, not to me: append `<date> proposal (<class>): <the line>` and, on the lines after it, indented, what it would have prevented — the findings or mistakes it is drawn from. The class is a short kebab-case name for the rule (`claude-md-git-version-noted`); when `<deferred>` already has the same rule, use its class, so the two count as one — the same rule in other words is the same rule, and a new class for it splits its count. A rule the project's `CLAUDE.md` already states is not proposed again: what went wrong is that it was not followed, which is a finding to fix, not a rule to add. A log of proposals alone is put off by the orchestrator without a review session, so keep to this shape. The proposals are collected and decided together once a month, by how often each comes back; one put to me in a session is decided on one data point, or lost in a report nobody answered. Mention in your report that you logged it, in a line.
